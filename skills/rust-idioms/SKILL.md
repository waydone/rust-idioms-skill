# Rust idioms, design & compiler-error diagnosis

Help the user write **idiomatic, correct, well-designed Rust** — and unblock them fast when the compiler says no. The user is AI-first and competent: give the *design reasoning* and the *root-cause fix*, not a syntax tutorial. Most of the value here is in: error-code → design-question mappings, type/ownership selection tables, the idiomatic choice among several that compile, and the gotchas that bite (especially around `async`/`Send` and lifetimes).

This skill is the **language layer**. It complements two things you likely already have:
- **salvo-skill** — the *framework* layer (Salvo API, routing, handlers, JwtAuth, OpenAPI). If the question is "how do I do X in Salvo", defer to that skill.
- **rust-analyzer-lsp** — the *tooling* layer (go-to-def, find-refs, types). If the user just needs navigation/lookup, the LSP answers directly; don't reach for this skill for that.

## Version discipline (read first)

This skill assumes **current stable Rust = 1.100** (rustc/cargo 1.100.0, 2026-11) and **edition 2024** (stabilized in Rust 1.85, Feb 2025 — still the newest edition; there is no later one).

**New on stable since 1.95 — reach for these instead of the older workaround** (each checked by compiling on 1.100.0):
- **1.96 `assert_matches!` / `debug_assert_matches!`** — replaces `assert!(matches!(..))` and prints the value on failure. ⚠️ Not in the prelude: `use std::assert_matches;` (and `use std::debug_assert_matches;`). Guards work: `assert_matches!(r, Err(E::Bad(s)) if s == "x")`.
- **1.98 `bool::ok_or(err)` / `ok_or_else(f)`** — `(!s.is_empty()).ok_or(Error::Empty)?;` instead of an `if … { return Err(..) }`. **`Option::map_or_default` / `Result::map_or_default`** — `opt.map_or_default(|s| s.len())` instead of `map_or(0, …)` / `map(..).unwrap_or_default()`.
- **1.99 `Vec::into_parts` / `Vec::from_parts`** and **`Box::into_non_null` / `Box::from_non_null`** — `NonNull`-based raw-parts round trips; prefer them to the `*mut`-based `into_raw_parts`/`from_raw_parts` dance in unsafe code.
- **1.99 legacy integer modules are fully deprecated** — write `i32::MAX`, never `std::i32::MAX` (now a `deprecated` warning). 1.97 deprecated the `std::char` constants/functions likewise (use `char::MAX`, `char::from_u32`).
- **1.100 the never type `!` is stable.** Write `Result<T, !>` for an API that cannot fail, and consume it with the irrefutable `let Ok(v) = r;` — no `unwrap`. `std::convert::Infallible` is now a **type alias of `!`** (the same type, so `Result<u8, Infallible>` *is* `Result<u8, !>`). Three things that bite: there is **no blanket `From<!>`**, so `infallible()?` inside a fn returning `Result<_, MyError>` is E0277 unless you add `impl From<!> for MyError { fn from(n: !) -> Self { n } }`; a crate that implemented a trait for both `!` and `Infallible` now gets E0119 (delete one); and inference falls back to `!` instead of `()` on every edition, so code that leaned on the `()` fallback needs an annotation.
- **1.100 the allocator API is stable** — `std::alloc::{Allocator, Global, System}`, `Vec::new_in(a)` / `with_capacity_in`, `Box::new_in(v, a)`, and the `Vec<T, A>` / `Box<T, A>` type parameter. Arena/bump allocation no longer needs nightly. `Vec<T, A>` is a *different type* from `Vec<T>` (= `Vec<T, Global>`): a `fn f(v: &Vec<u8>)` rejects it (E0308) — take `&[T]`, or be generic over `A: Allocator`.
- **1.100 small std wins:** `s.trim_prefix(p)` / `s.trim_suffix(p)` (str, slices, `Path`) replace `s.strip_prefix(p).unwrap_or(s)`; `Vec::from_fn(n, |i| ..)` replaces `(0..n).map(..).collect()`; `flag.toggle()`; `Box::map(b, f)` / `Rc::map` / `Arc::map` rebuild a smart pointer reusing the allocation when layouts match (associated fns — `Box::map` hands `f` the `T`, `Rc`/`Arc::map` hand it `&T`); **`std::mem::DropGuard::new(value, |v| cleanup(v))`** is a std scope guard (derefs to the value, `DropGuard::dismiss(g)` disarms and returns it) — reach for it before the `scopeguard` crate or a hand-written `Drop` struct.
- **Tooling:** Cargo `build.warnings = "deny"` (1.97, `.cargo/config.toml` `[build]`) replaces `RUSTFLAGS=-Dwarnings` in CI without invalidating the build cache; `cargo -m` = `--manifest-path`; edition-2024 workspace members may set `default-features = false` on an inherited dependency (1.99). **Cargo 1.100:** Cargo has its own lints under `[lints.cargo]`, and `cargo::unused_dependencies` is **warn by default** — a dependency nothing uses is now reported on every build (set `unused_dependencies = "deny"` in `[lints.cargo]` for CI, verified), so only list crates the code actually uses when scaffolding a `Cargo.toml`; `cargo install` honors the package's own `Cargo.lock` by default, so `--locked` is now a no-op (verified with `cargo install --path`: 1.99.1 re-resolved a dependency to its newest release, 1.100 built the locked version) — what you install is what the author tested, and a tool can no longer be "fixed" by reinstalling to pick up newer dependencies; a **publish-age cooldown** is built in — `[registry] global-min-publish-age = "7 days"` in `.cargo/config.toml` (or `CARGO_REGISTRY_GLOBAL_MIN_PUBLISH_AGE`) makes the resolver skip versions younger than that unless `Cargo.lock` already has them (verified: with a 5-day window `salvo = "1.1"` resolved to 1.1.1 instead of the 3-day-old 1.1.2; `[resolver] incompatible-publish-age = "allow"` turns it off) — a cheap guard against both supply-chain incidents and day-one regressions; intermediate artifacts moved from `target/<profile>/deps` + `.fingerprint` to `target/<profile>/build/<pkg>/<hash>/` (verified; the final binary is still `target/<profile>/<name>`), so scripts should locate artifacts through `--message-format=json`, not hard-coded paths. Behavior changes that can surface in old code — 1.100, each reproduced against 1.99.1: a closure no longer captures a place it only matches with non-binding patterns in `if let` (`|| if let (_, _) = t {..}` used to borrow `t`; now it captures nothing, which changes what a `move` closure owns and when things drop); `box` patterns are a hard syntax error even inside `#[cfg(false)]` code and unexpanded macro input (was a warning); `Iterator::max`/`min` now call `Ord::max`/`Ord::min` rather than `cmp`, and `max_by_key`/`min_by_key` compare through the `PartialOrd` operators — a type whose `PartialOrd` disagrees with its `Ord`, or that overrides `max`/`min`, returns different results. Also reproduced: projecting an associated type through a trait object of a dyn-**in**compatible trait — `type X = <dyn T<A = u8> as T>::A;` — compiled on 1.99.1 and is E0038 on 1.100. The single note that did not reproduce: `Box` impls generalized over allocators "may cause new type inference errors" — about 40 everyday `Box` conversions, comparisons and trait calls compiled identically on both toolchains, so expect it to be rare; if it does appear, annotate the `Box<T>` type. some ambiguous glob imports became hard errors (1.98); `pin!(x)` no longer deref-coerces a `&mut T` (1.97); a hand-written `PartialOrd` that disagrees with a derived `Ord` now misbehaves (1.98 fast path).

- **For a NEW project, use `edition = "2024"` — every time, in every `Cargo.toml` you write** (bins, libs, workspace members, proc-macro crates, throwaway repros, snippets in an answer). 2024 is the current edition and what `cargo new` / `cargo init` generate; prefer running `cargo new` over hand-writing the manifest. Do **not** emit `edition = "2021"` — that's a stale training-data default, not a conservative choice, and it silently opts out of edition-2024 behavior (e.g. the new `gen` keyword, RPIT lifetime capture rules, `unsafe extern`, disjoint closure captures already from 2021, `if let` temporary scope changes). When you scaffold a `Cargo.toml`, default to 2024.
- **For an EXISTING project, match what its `Cargo.toml` already declares** — don't "upgrade" the edition as a side effect of an unrelated change; an edition bump is its own deliberate task (`cargo fix --edition`).
- State the rust/edition you assumed when it matters, the way salvo-skill pins its target version. If a feature depends on a recent rustc, say so.

## Verify non-trivial third-party crate APIs with Context7

Your training data lags the current releases of `thiserror`, `anyhow`, `tokio`, `syn`/`quote`, `proptest`, `criterion`, `serde`, etc. For anything beyond textbook usage of these crates, query Context7 before writing the code (e.g. `tokio` 1.x `JoinSet`/`select!` semantics, `thiserror` 2.x attributes, `anyhow` 1.x context/downcast APIs, `syn` 2.x AST). Standard-library and language constructs (ownership, traits, `?`, iterators) you can write directly. When unsure, say the API is unverified and recommend `cargo check`.

## Standing rules

- **Root-cause over patch.** When code won't compile, explain *why* the design hit the wall and give the fix that addresses it — not a reflexive `.clone()`, `'static`, `Box::leak`, or `unsafe` that silences the checker while hiding the real issue. If a clone *is* the right call, say why.
- **Idiomatic, not just compiling.** Prefer the standard-library / community-idiomatic form. Note when a terser form exists.
- **Verify what you can.** Treat conclusions as needing `cargo check` (or `cargo test` / `cargo expand` / `miri` for macros/unsafe). Mark anything you couldn't run.
- This skill ships **no hooks, no MCP server, no background agents, and requests no extra permissions** — it is pure reference text loaded on demand.
